0.8.0 keeps your logs. Until now the admin UI streamed one container's output live from podman,
and once a container was replaced its lines were gone. hoster now stores what every managed
container prints, reads levels and fields from JSON lines, and records one row per request the
proxy routes to a stack. The stack's **Logs** tab and a new **Telemetry** page are built on top.
App repositories also get two GitHub Actions in place of copied curl and jq.

# A log store

Every line a managed container writes to stdout or stderr is now a record in the log store,
`logs.db`, a second SQLite file beside `hoster.db` in the state directory. Nothing changes in
your apps or stack files: hoster follows each managed container it starts or finds running until
it is removed, and takes the stack, service and generation from the container, not from the line.

- **Structured lines.** A line that is a JSON object gets its level, message and fields from the
  keys loggers commonly use (`level`, `severity` or `lvl`; `message`, `msg` or tracing's
  `fields.message`), including pino's and syslog's numeric levels. Any other line is kept whole
  with no level. Lines over 16 KiB are cut.
- **Retention.** Records are kept for 7 days. If `logs.db` grows past 1 GiB, the oldest hours go
  first, so a busy server keeps less than a week. Both limits are fixed.
- **A line-rate cap.** A container that prints more than 1000 lines in a second has the rest of
  that second dropped, with one `warn` record saying how many.
- **Restarts.** podman keeps capturing output while hoster is down. When hoster starts again it
  reads on from the last line it stored, so nothing is stored twice and the lines in between are
  picked up. If podman's size-capped log no longer holds all of them, a record says which lines
  were lost.
- **hoster's own events.** Deploy steps, health checks, certificate orders and restarts at
  `info` and above are stored too, as the service `hoster`, under the stack they are about. A
  failed health check sits right beside the app's own error. This does not follow `RUST_LOG`,
  and the journal is unchanged.

The System page has a new **Log store** card: the file's size against the 1 GiB cap, how far
back it reaches, the records and requests of the last hour, which limit decided the last cleanup,
and what was lost since hoster started (to the rate cap, a full queue or a failed write).
`hoster doctor` gains a `log_store` check that `logs.db` exists with mode `0600` and opens.

Whatever an app prints is now on disk for 7 days, secrets included, so don't log tokens or
passwords. [[logging|Logging from an app]] is a new guide with the details and with setups for
Rust's `tracing`, pino, Go's `slog` and aphid-server.

# A request log at the edge

The proxy stores one row per request it routed to a stack: arrival time, host and route, stack
and service, method, path (without the query string), status, time to the response header and in
total, response bytes, client address, and whether the app could not be reached or timed out.
A WebSocket is one row, written when it closes. Each request gets a request id.

Requests that never reach an app are not stored: unknown hosts and paths, port 80, the admin
host. The proxy never waits for the store; if it falls behind, rows are dropped and counted on
the System page.

The `hoster::access` line in the journal is now logged at `debug`, so it no longer shows by
default. The stored rows are the access log now. To get the journal lines back, see
[[install#operating-hoster|Operating hoster]].

# The new logs view

A stack's **Logs** tab now reads the store instead of one container's live stream:

- Every service's records merged in time order, with a coloured service column and hoster's own
  records under `hoster`. Chips pick the services, and records of replaced containers show
  their generation.
- A time range from 5 minutes to 7 days, with older and newer pages.
- Level chips (all, error, warn+, info, debug) and a grep field with an optional regex. Matches
  are marked in the message.
- A record with fields opens on them, and a click on a value lists only the records with that
  value, such as every line of one request.
- The newest page **follows** new records as they are stored, about once a second.
- A **source** switch: the containers' records, the **access log** (the stack's request rows,
  filtered by service, status, path and duration), or the stack's **deploy** events as log rows.
- **Download** the range as text or JSON lines, not only the page shown, up to 100,000 records.
  The access log downloads too.

In the access log, a request id links to the containers' records that mention it. That is a
text search: hoster doesn't pass the id to your app yet, so it only finds lines where the app
logged the same id on its own.

The new **Telemetry** page in the sidebar has a **Logs** tab with the same filters across every
stack, with a stack column and selector (`hoster` for hoster's own records that name no stack),
over the last 15 minutes by default. Above the records, a severity histogram shows the levels
over the range, and each bar links to the logs of its time. Following, downloading and the
source switch stay on the stack's tab.

Each container's live log, straight from podman, is still at `/containers/{name}/logs`, linked
from the logs tab. It shows a line before it is stored and works when the store is unavailable.

See [[overview#the-admin-ui|The admin UI]] and [[logging]].

# GitHub Actions for app repositories

Two composite actions now ship with each release, used from the tag the server runs:

- **`LHelge/hoster/actions/deploy@v0.8.0`** replaces about 30 lines of curl and jq. It requests
  the OIDC token and posts to the deploy webhook. Inputs: `url` (the admin URL), `stack`,
  `images` (one `service=digest` per line, deployed together), and optionally `audience` (only
  when `[webhook] audience` is set) and `tag` (for the deploy history). It fails with hoster's
  reason, retries `502`, `503` and connection failures with a fresh token, outputs `result`,
  `deployment-id` and `deployment-url`, and links the deployment in the job summary. The job
  still needs `permissions: id-token: write`.
- **`LHelge/hoster/actions/stack-check@v0.8.0`** downloads the release binary for the runner,
  verifies it against `SHA256SUMS` and runs `hoster stack check` on `files` (globs work). Each
  error and warning is annotated on its line. `version` picks the release (default `latest`,
  better pinned to the server's) and `deny-warnings` fails on warnings too.

The webhook itself is unchanged, so existing curl workflows keep working. See
[[deploying-from-ci#2-3-deploy-with-hoster-s-action|Deploying from CI, §2.3]] and
[[deploying-from-ci#2-6-check-the-stack-file-on-every-push|§2.6]].

# Updating

```sh
hoster update
```

Or use *Update* on the System page. Nothing changed in `hoster.toml`, in the stack format, in
hoster's database or in the systemd unit, so there is nothing to edit and no reason to run the
install script again.

On first start hoster creates `logs.db` in the state directory and starts following your
containers. For the ones already running, it first stores what podman still holds of their logs,
at the times podman stamped them, so the logs tab is not empty after the update. Plan for up to
1 GiB of disk for it. `hoster backup db` does not include it, and you
don't need to back it up: a restored server starts with empty logs ([[backup]]).

Rolling back to 0.7.0 is safe. `hoster rollback` now handles `logs.db` too, but 0.7.0 has no log
store, so the file is left as it is and 0.7.0 ignores it. Update again later and 0.8.0 reads on
from where it stopped, as far back as podman's logs still reach. From later releases, a rollback undoes
`logs.db`'s schema like `hoster.db`'s, and if that fails it moves the file aside rather than failing the rollback (see
[[install#updates-and-rollback|Updates and rollback]]).
