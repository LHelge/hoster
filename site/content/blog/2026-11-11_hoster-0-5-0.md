0.5.0 is about running images you didn't build: give them their config files, cap what they
can use, and write their stack files in an editor that checks them as you type. A new guide,
[[third-party-images]], walks through translating a compose file.

# Config files in containers

A service can now get files written into its container before it starts, either from text in
the stack file or from one of the stack's secrets:

```toml
[services.prometheus.files]
"/etc/prometheus/prometheus.yml" = { content = """
global:
  scrape_interval: 15s
""" }
"/etc/prometheus/web.yml" = { secret = "monitoring/web-config", mode = "0440", owner = "0:65534" }
```

A change to a file's content or its secret redeploys the service, like an environment variable.
The stack overview lists each service's files with their mode, owner and size, but never their
content. Stacks with `files` need podman 5.4 or later; hoster refuses them on an older podman
and says which version it found. See [[stack-format#2-2-1-config-files-adr-0057|Config files]].

# Resource limits and runtime options

A `limits` table caps one service so it can't starve the host, hoster or the proxy:

```toml
[services.worker.limits]
memory = "512MiB"   # hard, no swap
cpus = 1.5
pids = 256
```

Nothing is limited unless you set it. When a container is killed for running out of memory,
hoster now says so: restart events, crash-loop details, dashboard warnings and failed deploys
read "OOM-killed (limit 512MiB)" instead of just "exit 137". The stack overview shows each
service's limits. See [[stack-format#2-2-3-resource-limits-adr-0059|Resource limits]], including
why a start-first deploy can briefly use twice a service's limits.

Three runtime options cover what common images expect: `shm_size` for databases and browsers
that need a bigger `/dev/shm`, `tmpfs` for sized in-memory mounts (handy with `read_only`), and
`init = true` to run podman's init as PID 1 for images that leave zombie processes behind. See
[[stack-format#2-2-2-shared-memory-tmpfs-and-init-adr-0059|Shared memory, tmpfs and init]].

Sizes are written with a unit, as `"512MiB"` or `"2GB"`. A bare number or Docker's `512m` is
an error that suggests the right spelling.

# A stack editor in the admin UI

The New stack page has a real editor now: TOML highlighting, line numbers, and Tab and Enter
that indent the way you'd expect. A moment after you stop typing it checks the file the way an
apply would (validation, route collisions, unset secrets, the podman version), without
resolving any images, and marks the problem lines. Beside it are a field reference generated
from the stack format and snippets you can insert. An empty editor starts from a skeleton.

**Edit stack file** on a stack's page opens its active file in the same editor. If someone else
deploys a new revision while you edit, the preview warns you before you apply.

# Updating

```sh
hoster update
```

Or use *Update* on the System page. Nothing changed in `hoster.toml`, and nothing changed in
hoster's database, so rolling back to 0.4 is safe. Existing stack files keep working as they
are, and their containers are not recreated.

Two of the new keys need something on the host that `hoster update` can't set up. Re-running
`install.sh` adds both, or see [[install#cgroup-delegation-and-catatonit|Cgroup delegation and catatonit]]:

- `limits` need the `cpu`, `memory` and `pids` cgroup controllers delegated to hoster's user.
  systemd 252 and later do that by default; Ubuntu 22.04 doesn't delegate `cpu`. `hoster doctor`
  tells you. If one is missing, a stack that uses it is rejected with the fix in the message.
  Applying the delegation restarts hoster's user manager, which stops hoster and its containers
  briefly, so `install.sh` only prints the command while hoster is running.
- `init = true` needs `catatonit` installed.
