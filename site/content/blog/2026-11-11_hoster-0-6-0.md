0.6.0 gives the admin UI a memory and keeps your third-party images current. Traffic figures
are now a history that survives restarts, drawn as charts over a range you pick. And hoster
checks the images you didn't build for updates, shows them, and applies them by itself where
you ask it to.

# Traffic history and charts

Until now the dashboard counted requests since hoster started, so every restart and update
wiped it. hoster now records the traffic to each route once a minute and keeps it: one record
per minute for the last 24 hours and one per hour for the last 60 days.

The **dashboard** has a range picker (1h, 6h, 24h, 7d and 30d; 24h by default). The requests,
5xx rate, p50 and p95 tiles cover the range and show the change against the period before it.
Two new charts draw the responses by status and p50/p95 over time. The stacks table gains
requests per minute and a sparkline for each stack.

The **stack pages** show the last hour. Each card on Stacks has requests per minute, p95, the
5xx share and a sparkline. A stack's overview has requests per minute with the hour's busiest
minute, p50, p95, the 5xx rate and a chart of its responses by status.

A few things to know:

- The figures are up to a minute behind, and requests per minute is the rate over the last 5
  minutes. Only the requests in flight are live.
- The history starts with this release, so the charts fill in from the moment you update, and
  a change "vs prev" appears once the period before has data.
- The stack overview's slowest-routes card is gone. It only counted since hoster started.
- The history lives in hoster's database, so `hoster backup db` copies it. A route that is
  busy every minute takes about 0.7 MB in total; idle routes take nothing.

See [[overview#traffic-history|Traffic history]].

# Updates of third-party images

hoster now checks every tagged third-party image for updates in the background, every 6 hours
by default (Settings → Updates, with a *Check now* button). It finds tags that moved to a new
digest, such as a rebuilt `postgres:17`, and newer versions in the same line of tags, such as
`v2.3.1` → `v2.4.0`. Pre-releases are never offered.

What it finds is shown on the stack's card and overview, majors marked as such. **Update**
opens the usual apply preview with the new tag written into the stack file, comments and
formatting kept.

A service can also opt in to updates hoster applies by itself:

```toml
[services.db]
image = "docker.io/library/postgres:17"
auto_update = "digest"    # moved tags only

[services.server]
image = "ghcr.io/immich-app/immich-server:v2.3.1"
auto_update = "minor"     # moved tags, patch and minor versions
```

The default is `"off"`: updates are shown, never applied. A major version is never applied
automatically, whatever the policy. Services of one stack whose images share a registry,
namespace and tag move together, under the strictest policy among them. An automatic update is
an ordinary deployment with health checks and rollback, each update is tried once, and you are
only mailed when one fails.

See [[stack-format#2-2-4-updates-of-third-party-images-adr-0061|Updates of third-party images]]
and [[third-party-images#1-4-choosing-an-auto-update-policy|Choosing an auto_update policy]].

# Updating

```sh
hoster update
```

Or use *Update* on the System page. Nothing changed in `hoster.toml`. Existing stack files keep
working as they are, their containers are not recreated, and nothing is updated automatically
until you set `auto_update`.

This release adds tables to hoster's database. `hoster rollback` to 0.5 removes them again, and
with them the traffic history and the updates found so far; see
[[install#updates-and-rollback|Updates and rollback]].
