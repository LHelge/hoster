0.4.0 can mail you when something needs you, starts a stack's services in the order they depend
on each other, and lets you check a stack file before it reaches the server.

# Mail notifications

hoster now mails you when a deploy fails or is rolled back, a service starts crash looping or
turns unhealthy, a certificate can't be issued or renewed, a host's DNS stops pointing at the
server, or hoster rolls itself back after an update. It mails you again when the problem is over. A crash-looping service or a retrying certificate sends one mail, not one per attempt;
if a problem lasts, a reminder follows after 24 hours. At most 20 mails go out in an hour, and
anything beyond that arrives as one summary. You can also ask for mail on successful deploys and
renewals.

Mail goes to one recipient through [Resend](https://resend.com), the first supported provider.
Set it up under **Settings → Notifications**: the API key, a sender on a domain you have verified
at Resend, and the recipient. **Send test** checks the setup right away. If a mail can't be
delivered (a revoked key, an unverified sender, a used-up quota), the page says why and the
Events page records it. Notifications are off until you set them up. [[notifications]] has the
details and the limits: nothing is sent while hoster or the host is down.

**Settings → General** also gets an **Instance name**. It is shown in the sidebar and in mail
subjects, so you can tell your servers apart. Until you set one it is the hostname, as before.

# Dependencies and exec health checks

A service can name the services it needs:

```toml
[services.app]
depends_on = ["db", "cache"]
```

Deploys start `app` only once `db` and `cache` pass their health checks, and so does hoster after
a reboot or a crash. The apply preview shows the start order, and the stack overview shows what a
service is waiting for. A cycle is rejected with the services named in order.

Health checks gain `exec`, a command run inside the container, such as
`exec = ["pg_isready", "-U", "app"]`. It works on any service, including one without routes, which
could only use the default "running for 5 s" check before. See [[stack-format]].

# Check a stack file before deploying it

`hoster stack check deploy/app.stack.toml` validates a stack file the way the server does,
without a server: on your machine or as a step in CI, with `--deny-warnings` to fail on warnings
too. [[deploying-from-ci]] has a GitHub Actions example.

There is also a JSON Schema for stack files at `https://docs.hoster.lhelge.se/stack.schema.json`.
Put `#:schema https://docs.hoster.lhelge.se/stack.schema.json` on the first line of a stack file
and editors with TOML schema support complete keys and flag mistakes as you type. A running hoster
serves the schema of its own version at `https://<admin host>/schema/stack-v1.json`.

# Updating

```sh
hoster update
```

Or use *Update* on the System page. Nothing changed in `hoster.toml`. Existing stack files keep
working as they are; `depends_on` and `exec` are new keys you can add.

hoster no longer lets podman run an image's own `HEALTHCHECK`. hoster never used it, but podman
ran it on a timer anyway. Containers created before the update keep that timer until they are
next recreated.

The update adds tables for the instance name and the notification settings to hoster's database.
Rolling back to 0.3 removes them, so you would have to set both up again.
