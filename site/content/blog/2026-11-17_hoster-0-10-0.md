0.10.0 shows the spans that 0.9.0 started storing. The **Telemetry** page has a new **Traces**
tab with a list of traces, a duration chart and a waterfall for the trace you pick. Traces and
log records now link both ways. A JSON line your app prints on stdout links to its trace too, as
long as it names the trace and span ids.

Nothing needs editing to update. See [Updating](#updating).

# The Traces tab

**Telemetry → Traces** is now the Telemetry page's first tab, and `/telemetry` opens it. It
lists every trace whose root span started in the range, across all stacks or for the one you
pick.

- **The list** shows the root span's start and name, the stack, the services as coloured chips
  (the proxy's spans are `hoster`), the span count, the duration and the status. **app not
  instrumented** marks a request whose app was called but sent no spans of its own.
- **Range, sort and filters.** The range runs from 5 minutes to 24 hours, since spans are kept
  for 3 days. You can sort by newest, slowest or errors first, and filter by status, by *slower
  than* a root duration such as `500ms`, or by a grep on span names.
- **The duration chart** above the list draws every trace in the range as a dot: its start
  across, its duration up on a log scale, and errors in red. It follows the list's filters. The
  traces on the current page are rings you can click to open them.
- **Everything is in the URL**, including the selected trace and span, collapsed rows and the
  critical-path switch, so any view can be bookmarked or linked.

# The waterfall

The selected trace opens below the list as a waterfall. The header shows its duration, span
count, depth and errors, followed by a legend of services, a minimap of the whole trace, and one
row per span on a shared time axis. Spans in error are marked red. A tag shows what a span calls
(`pg`, `redis`, `exec`, …), and a span whose parent never arrived is marked *parent missing*.

- **Span details** open under the selected row. They show its start, duration, self time and
  parent, its attributes and resource, its events (with an exception's stack trace), and the
  first 50 log records it wrote. A trace opens on the span where it went wrong, or on its root
  when nothing failed.
- **Collapse** any span with children, or use **collapse to services** to read a trace as the
  services it passed through. **expand all** undoes both.
- **critical path** dims every span the trace did not wait for. It stays on as you move between
  spans and traces.
- **The page stays put.** Selecting, collapsing and the critical-path switch update the
  waterfall in place without scrolling. Without JavaScript they reload the page and land on the
  waterfall.

The [[tracing#the-traces-tab|Traces tab]] section of the tracing guide covers all of it.

# Traces and log records link both ways

- **A TRACE column** ends every row on the stack's **Logs** tab and on Telemetry → Logs. It
  links the record to its span in the Traces tab, or shows `—` when the record has no trace.
  The access log has the column too: a request's trace is the one the proxy started for it.
  Requests stored before 0.9.0 have none.
- **`?trace=<trace id>`** narrows a Logs tab to one trace's records and shows a chip you can
  remove. Without a `since`, it searches the whole 7 days the store keeps.
- **From the waterfall**, **logs in trace (N) →** opens all of the trace's records, and each
  record in the span details links to the Logs tab, starting at that record.
- **An opened record** lists `trace_id`, `span_id` and `service.name` after its fields.

# Trace ids from JSON lines on stdout

Until now, only log records sent over OTLP carried trace and span ids. A JSON line on stdout or
stderr now carries them too when it names them:

```json
{"level":"info","msg":"order paid","trace_id":"4bf92f3577b34da6a3ce929d0e0e4736","span_id":"00f067aa0ba902b7"}
```

hoster reads `trace_id` or `traceId` and `span_id` or `spanId`, at the top level or under
`fields`, when they are well-formed W3C ids. A span id counts only beside a trace id. An app can
now send spans over OTLP and keep its logs on stdout without losing the links between them. See
[[logging#trace-and-span-ids|Trace and span ids]].

The ids that hoster reads move out of the record's fields. Lines stored before the update keep
them as fields.

# Updating

```sh
hoster update
```

Or use *Update* on the System page. Nothing changed in `hoster.toml`, the systemd unit or the
deploy actions. There is nothing to edit, no need to run the install script again, and stacks
don't need redeploying.

- **`/telemetry` opens Traces now.** A bookmark to it used to land on the logs. That tab is at
  `/telemetry/logs`.
- **A field filter on `trace_id`** (a field chip clicked before the update, saved in a URL)
  no longer matches new JSON lines, because their id is no longer a field. Use the
  `?trace=` filter instead.
- **The log store gets a new index** on its records' trace ids. hoster adds it to `logs.db` on
  first start.

Rolling back to 0.9.0 is safe. `hoster rollback` drops the index and the Traces tab goes away
again. Stored spans and records stay. See
[[install#updates-and-rollback|Updates and rollback]].
