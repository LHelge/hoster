0.11.0 lets you take the traces you are looking at out of hoster: the **Traces** tab can now
download, copy or open the trace list as plain text written to be pasted into a model
session. It also fixes two recovery cases: a redeploy now recreates containers that are
missing, as on a freshly restored host, and recovery no longer starts a stop-first service while
its old container may still be running.

Nothing needs editing to update. See [Updating](#updating).

# Exporting traces

Beside the trace list on **Telemetry → Traces**, three new links export the traces the list
shows, as it stands: its range, stack, filters, sort and page.

- **Copy** puts the text on the clipboard and says "Copied" beside the links.
- **Download** saves it as `traces-<stack or all>-<start>-<end>.txt`.
- **Open as text** shows it in the browser.

The text starts with a header saying the range, stack, filters and which traces of how many
it holds. Each trace follows as a summary line, then its spans as an indented tree with their
service, name, kind, duration, status and attributes, and their events and log records under
them. It is capped at 2,000 spans, 200 characters a value and 20 records a span, and every cut
says what it left out, so a model knows what it is not seeing.

Copy needs JavaScript and a browser that lets the page use the clipboard, which most allow only
over HTTPS. Without them the button is not shown, and Open as text still works. All three use
`/telemetry/traces/export` with the list's options, so a script signed in to the admin UI can
fetch the same text. See [[tracing#exporting-traces|Exporting traces]].

# Fixes

- **Redeploy recreates missing containers.** Redeploying a deployment from the
  **Deployments** list now creates the containers of its generation when they are gone, rather
  than only expecting them to be there. That is the step a restore onto a fresh host was
  missing: startup reconciles what Podman has, and a fresh host has none of the containers yet.
  The restore steps in [[backup#restoring|Restoring]] now say to redeploy the most recent
  deployment that went live for each stack, once the database and volumes are back.
- **Stop-first recovery waits for the old container.** When recovery could neither stop nor
  remove a service's obsolete generation, it used to go on and start the committed one anyway,
  so a `stop-first` service could briefly run twice. It now holds that service until the old
  container is confirmed gone, and resumes on a later pass.

# Updating

```sh
hoster update
```

Or use *Update* on the System page. Nothing changed in `hoster.toml`, the systemd unit, the log
store or the deploy actions. There is nothing to edit, no need to run the install script again,
and stacks don't need redeploying.

Rolling back to 0.10.0 is safe; the export links go away again. See
[[install#updates-and-rollback|Updates and rollback]].
