0.9.0 lets your apps send OpenTelemetry traces and logs to hoster without configuration, and
starts a trace for every request the proxy routes. The deploy action can now wait for a rollout
and fail the CI run when it does not go live. Two fixes came out of deploying a larger app:
client addresses in `X-Forwarded-For` are plain IPv4 again, and the logs page no longer scrolls
far past its box.

**Read [Updating](#updating) first:** the first deployment of each stack after the update
replaces all of its services, even where nothing changed.

# Traces and logs over OTLP

hoster now has an OTLP receiver. An app with an OpenTelemetry SDK can export spans and log
records to it, and hoster keeps them in the log store beside the lines your containers print.

- **Nothing to configure.** Every service gets the standard `OTEL_*` variables: the endpoint
  `http://host.containers.internal`, the protocol `http/protobuf`, `OTEL_SERVICE_NAME`, a
  bearer token of its own in `OTEL_EXPORTER_OTLP_HEADERS`, and resource attributes naming the
  stack and the deployment. An SDK that reads its environment exports with no endpoint or token
  in the stack file. A variable the stack file sets itself wins.
- **Reachable only from your containers.** The receiver is served by the proxy's existing port
  80 as `host.containers.internal`. It answers only peers with one of the host's own addresses,
  so no port is opened and nothing is public. That name is now reserved: a stack file cannot
  route it. `hoster doctor` checks that a container can reach the receiver.
- **The token decides where data goes.** Exports are stored under the stack and service the
  token names, whatever the payload's `service.name` says.
- **OTLP over HTTP with protobuf bodies**, plain or gzip: `/v1/logs` and `/v1/traces`. gRPC,
  OTLP's JSON encoding and metrics are not accepted.
- **Kept:** spans for 3 days, log records for 7 days like printed lines. All of it shares the
  log store's 1 GiB cap. Each service may send 1000 records and 1000 spans a second, sustained;
  what goes over is dropped and marked with one record per gap.

Exported log records show up in the stack's **Logs** tab and on the **Telemetry** page with the
stream `otlp`, their attributes as fields. Spans are stored from now on, but the trace views
that show them come in a later release.

If your app already prints JSON lines on stdout, don't export the same logs over OTLP too, or
each line is stored twice. [[tracing|Traces and logs over OTLP]] is the new guide, with setups
for Rust's `tracing` and aphid-server.

# A trace for every request

The proxy now starts a trace for every request it routes to a stack, and sends the app a W3C
`traceparent` header. The trace id is the request's id in the stack's access log.

- An app whose SDK continues the incoming trace gets its spans nested under the proxy's, and the
  log records it exports inside them carry the same trace id.
- An app with no SDK still has a two-span trace per request: the proxy's server span and its
  span for the call to the app, kept with the request's row in the access log.
- A `traceparent` or `tracestate` sent by the client is removed and never reaches your app, so a
  trace always starts at hoster's edge.

# The deploy action can wait for the rollout

A green CI run used to mean only that hoster **accepted** the deploy. A rollout that failed its
health checks, and so kept the old containers, still looked green in GitHub. Now the deploy
action can wait:

```yaml
- uses: LHelge/hoster/actions/deploy@v0.9.0
  with:
    url: https://hoster.example.com
    stack: notes
    images: |
      api=${{ steps.push.outputs.digest }}
    wait: true
    timeout: 15m   # the default is 10m
```

With `wait: true` the step follows the deployment until it is over. It succeeds when the
deployment goes live, with a warning if it went live with warnings. It fails, with hoster's
state and reason, when the deployment fails, is rejected, is superseded by a newer deploy, or is
still running at `timeout`; in that last case the deployment keeps running in hoster. The job
summary says how it ended, and a new `state` output carries the final state. Without `wait`, the
action behaves as before.

The action follows the deployment through a new endpoint,
`GET /hooks/deploy/{stack}/deployments/{id}`, with the same OIDC token the deploy sent. A read
does not use the token up, and it shows only the deployments the same workflow run started. You
can poll it yourself from other CI systems; see
[[deploying-from-ci#2-4-without-the-action|Deploying from CI, §2.4]].

`wait` needs a server running 0.9.0 or later. Against an older hoster the step fails, saying
the server has no status endpoint, so update the server before you add `wait` to a workflow.
The inputs are in [[deploying-from-ci#2-3-deploy-with-hoster-s-action|§2.3]].

# Fixes

- **Client addresses are plain IPv4.** The proxy listens on IPv4 and IPv6 at once, so an IPv4
  client arrived as an IPv4-mapped IPv6 address, and `X-Forwarded-For` carried
  `::ffff:203.0.113.9` instead of `203.0.113.9`. That made app logs harder to read and grep,
  could put every IPv4 client in one rate-limiting bucket of an app that groups IPv6 clients by
  /64, and could keep a trusted-proxy range written as IPv4 from matching. hoster now uses the
  plain IPv4 form everywhere: in `X-Forwarded-For`, in the access log (older rows included), and
  for the per-address connection cap. Real IPv6 clients are unchanged.
- **The logs page scrolled far past the log box.** Hidden labels inside the log rows stretched
  the page to the log's full height. Fixed on the stack's **Logs** tab, on Telemetry → Logs and
  on the live container log, and in two scroll boxes on the apply page.

# Updating

```sh
hoster update
```

Or use *Update* on the System page. Nothing changed in `hoster.toml` or in the systemd unit, so
there is nothing to edit and no need to run the install script again.

- **Each stack's next deployment replaces all of its services.** The new `OTEL_*` variables are
  part of every service's configuration, so the first deployment of each stack after the update
  replaces every service, by its update strategy, even if no image or stack file changed. A
  stop-first service has its usual short gap. Nothing redeploys by itself: a container gets the
  variables, and starts exporting, when it is next replaced. To do it at a time of your choosing,
  redeploy each stack from its page.
- **Apps see two new things in requests:** a `traceparent` header from the proxy, and
  `X-Forwarded-For` with plain IPv4 addresses. An app that matched the `::ffff:` form, or an
  allowlist written in that form, needs the plain IPv4 address now.
- **The receiver needs podman 5.4 with passt 2024_08_14 or later** for containers to resolve
  `host.containers.internal`. Every distribution with podman 5.4 we checked has it, and
  `hoster doctor` reports it when a container cannot reach the receiver. Without it, hoster runs
  as before and only the export is lost.
- **The log store gets new tables.** hoster migrates `logs.db` on first start.

Rolling back to 0.8.0 is safe. `hoster rollback` undoes the log store's new schema, which
deletes the stored spans and the log records received over OTLP; printed lines and the access log
stay. The `OTEL_*` variables go too, so each stack's next deployment replaces its services once
more. See [[install#updates-and-rollback|Updates and rollback]].
