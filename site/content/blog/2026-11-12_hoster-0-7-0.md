0.7.0 shows what your containers and your host use, and makes the edge harder to wear down.
The admin UI gets CPU, memory and disk meters. The proxy now caps connections, times out idle
and stalled clients, and keeps scanner noise out of the log.

# Resource usage in the admin UI

Every page now has a **HOST** card at the bottom of the sidebar with the host's CPU, memory and
disk. Disk is the filesystem podman keeps its images and volumes on. Each figure has a meter
that turns orange from 80 % and red from 95 %, and CPU and memory have a line of the last hour.

A stack's overview adds **CPU** and **Memory** columns to its services table, one figure per
container. CPU is a percent of one core, so `150%` is one and a half cores. Memory is what
`podman stats` shows. Where a service sets `limits.cpus` or `limits.memory`, the figure is shown
against the limit with a meter in the same colours. The columns update while the page is open.

A few things to know:

- hoster samples every 10 seconds and keeps an hour in memory only. The lines start empty after
  a restart or an update, and nothing is added to the database.
- A figure hoster could not read, such as when podman does not answer, shows as `—`. It never
  slows down or breaks a page.
- The sidebar card refreshes itself, but that does not count as activity: a tab left open still
  signs you out after the idle timeout.
- The System page also shows the disk of hoster's data directory when it is on a different
  filesystem from podman's storage.

See [[overview#resource-usage|Resource usage]].

# A harder edge

hoster faces the internet directly, so this release looked at what a hostile client can do to
the proxy, and closed what it found:

- **Connection caps.** hoster raises its open file limit to 16384 at startup, and the unit sets
  `LimitNOFILE=16384` too. It refuses new clients while 4096 descriptors are open, and refuses
  more than 256 open connections from one IPv4 address or one IPv6 /64. Apps, the admin UI,
  SQLite and podman keep working at the cap. Refusals are counted and shown on the System page
  with the open files and the limit.
- **Timeouts.** An idle kept-alive HTTP/1.1 or HTTP/2 connection is closed after 60 seconds. A
  client that stops reading a response no longer holds its request open until a deploy's drain
  gives up. Client reads and writes now follow the route's `read` and `write` timeouts, so a
  quiet WebSocket on a route that allows longer is no longer cut at 60 seconds.
- **Request smuggling.** About 150 malformed and conflicting requests were sent through the proxy.
  None got through as anything but one cleanly framed request. One lenient spot is fixed: an
  upstream now always gets a single `Content-Length`.
- **HSTS on the admin host.** The admin UI now sends `Strict-Transport-Security` (one year, the
  admin host only), so a browser that has visited it once never goes there over plain HTTP.
  Your apps' hosts are left alone: whether an app wants HSTS is up to the app.

# Quieter logs

A server on a public address is probed all day. Until now each failed TLS handshake (every port
scan) logged an `error`, and each request to an unknown host logged an access line. Both are now
logged at `debug` and hidden by default. Real proxy errors and the access lines of your routes
are unchanged, and the dashboard still counts unrouted requests. To see the scanners again, see
[[install#operating-hoster|Operating hoster]].

# Smaller changes

- The routes on the stack cards and the stack page's Routes card are links that open the routed
  URL in a new tab.
- **Ubuntu 26.04**: stopping or removing the last running container no longer fails with
  "rootless netns: kill network process: permission denied". An AppArmor rule missing from 26.04's
  passt package caused it; the container was stopped all the same, and hoster now treats it as
  done and logs a warning.

# Updating

```sh
hoster update
```

Or use *Update* on the System page. Nothing changed in `hoster.toml`, in the stack format or in
hoster's database, so rolling back to 0.6.1 is safe.

`hoster update` does not replace the installed systemd unit. That doesn't matter for the
connection caps: hoster raises its own open file limit at startup, so they work with the unit
you have. To get the new unit with `LimitNOFILE=16384` anyway, run the install script again
before updating. It only replaces the unit when it differs and never restarts hoster (see
[[install#what-the-script-does|What the script does]]).
